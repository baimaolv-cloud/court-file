# 诉讼文书制作工作流

## 完整流程概览

```
信息采集 → 结构搭建 → 逐段撰写 → 证据编号管理 → 金额核算 → 法条核对 → 策略决策 → 多遍审定 → 导出定稿 → 网上立案
```

---

## 一、信息采集

### 当事人信息
- 自然人：姓名、身份证号、住址、职业/职称、联系方式
- 法人/其他组织：全称、统一信用代码、住所、法定代表人、注册资本
- 收集顺序：先原告后被告，多人时编号标注

### 事实材料
- 时间线：按时间轴排列所有关键事件
- 合同/交易记录：合同文本、支付凭证、沟通记录
- 损害证据：损失清单、发票、评估报告
- 行政维权记录：投诉编号、受理机关、处理结果

### OCR工具链
- **PDF有文本层**：直接用 PyMuPDF 提取
- **PDF扫描件**：`sips` 转 PNG → Swift Vision 框架 OCR
- **红/金底色证书**：OCR效果极差，按文件名列出即可，不强行识别
- **手写体/签名**：置信度低，不可靠
- **中文文件名**：转PNG时需用英文输出路径，否则路径解析可能失败
- **分辨率**：低分辨率PNG（<50KB）OCR严重缺失，需高分辨率重转

## 二、结构搭建

### 民事起诉状标准结构
```
标题：民事起诉状
原告信息（每人一段）
被告信息（每人一段）
案由
诉讼请求（分项编号）
事实与理由（按案由分部分）
  - 每部分：事实陈述 → 法律适用 → 赔偿计算
证据清单（编号连续）
管辖依据
此致 XXX人民法院
具状人签名
日期
```

### 多案由合并
- 按主次排列，主案由在前
- 每个案由独立成"部分"，内部自成体系
- 最后单独设"案由关联性"部分论证合并审理依据（民诉法第55条）

### 多原告/多被告结构
- 原告/被告分别编号（原告一/二/三，被告一/二/三/四）
- 首次出现用全称+编号，后续统一用"原告N""被告N"
- 账号、合同、付款方必须对应到具体原告编号

## 三、逐段撰写

### 论证风格决策
- 用户倾向强硬确定性→用"因果关系不言自明"替代"不排除系参考"
- 法律定性用语精确→先定性后论证，不给对方留空间
- 事实与法律交织→每段事实陈述后紧跟法律适用

### 常见段落模板
- **电子侵入**：技术能力→利益驱动→行为异常→产品印证→法律定性
- **掠夺性定价**：定价行为→成本对比→排挤效果→历史模式→法律适用
- **消费欺诈**：促销承诺→付款事实→违约事实→欺诈定性→法律适用
- **合同违约**：合同订立→被告违约→损害后果→法律依据

### 政策性论证（高阶）
对涉及AI、平台经济、反内卷等新型案件，需对接四级政策体系：
1. **政治局会议**（最高层，政治定性）
2. **国务院文件**（国发〔2026〕X号，行政法规）
3. **部委通知**（市监总局/最高法司法解释，执行依据）
4. **地方高院意见**（省高院，管辖法院政策环境）

引用格式：`"依据2026年4月28日中央政治局会议精神/国发〔2026〕7号文/市监总局5月14日通知/最高法法释〔2026〕7号/浙江高院16条意见……"`

## 四、证据编号管理（最容易出错的环节）

### ⚠️ docx证据编号重编——高危操作（2026-05-23血泪教训）

**结论：能不在docx XML中做就不在docx XML中做。**优先回到md源文件操作，再重新导出docx。

如果必须在docx中操作（如用户只提供了docx没有md）：

1. **解包前先备份**：`cp original.docx original_backup.docx`
2. **全面审计段落结构**：解包后统计numPr属性分布，区分自动编号段和手动编号段
3. **建完整映射表**：旧号→新号，JSON持久化，映射完成前不动文件

6. **替换后全量验证**：逐项搜索每个新编号确认上下文

### 证据文件按编号打包映射

**流程**：
1. 全盘扫描建文件索引（`find /path -type f > index.txt`）
2. 读取证据清单，建立编号→证据名称映射
3. **人工精确映射**：编号→文件路径（自动匹配只作辅助建议）
4. 复制重命名（`证据NNN_简称.ext`）
5. 打包ZIP
6. 验证：统计覆盖编号数+缺失编号，生成对照清单

**映射注意事项**：
- 一个编号可能对应多个文件（如#34有14篇论文、#31有7张火车票）
- 无实体文件≠遗漏，区分三类缺失：
  - **电子数据**（GitHub链接、账号）：当庭演示或补公证
  - **公开可调取**（年报、政策文件）：法院调取
  - **重复**（已在其他编号中）：标注"已在#XX"
- zsh中文路径glob不可靠，必须用`find`命令
- 子编号提升后映射关系复杂，用JSON持久化映射表

### 核心规则
1. **连续编号**：从1开始，不留空缺、不跳号、不重复
2. **禁止子编号**：不用"78-1""80-2"等，直接连续编号
3. **格式统一**：正文引用和证据清单格式一致（如"证据86(16)"）
4. **兜底条款**：最后一项设"其他相关证据"预留

### 新增证据操作规范
1. 在清单末尾追加新证据
2. 如需插入中间位置→重新编号后续所有证据
3. **必须**同步更新正文中所有后续证据的引用编号
4. 用Python脚本批量重编号（比sed更可靠）

### 批量重编号脚本模板
```python
import re
with open(filepath, 'r') as f:
    text = f.read()

# 映射表：旧号→新号（从大到小排序）
mapping = sorted([(80,79), (81,80), ...], reverse=True)

for old, new in mapping:
    # 使用负向前瞻，避免误伤证据800、证据80-1等
    text = re.sub(rf'证据{old}(?!\d)', f'证据{new}', text)

with open(filepath, 'w') as f:
    f.write(text)
```

### ⚠️ 批量替换三大雷区
1. **sed/正则误伤**：替换"证据80"会误伤"证据80-1""证据800"→用负向前瞻 `(?!\d)`
2. **替换顺序**：从小到大替换会导致新编号被二次替换→必须从大到小
3. **上下文检查**：替换后必须全文搜索每个新编号，确认上下文正确

### 证据↔论证交叉引用表（维护方法）

在证据清单末尾维护一张映射表（不写入诉状，存于工作区）：

```markdown
# 证据↔论证交叉引用表

| 证据号 | 证据名称 | 正文引用位置 | 论证目的 |
|--------|----------|-------------|---------|
| 证据25 | 腾讯2025年报 | 事实与理由一.(二) | 证明腾讯AI投入/垄断地位 |
| 证据86 | 消费欺诈截图16张 | 事实与理由三.(一) | 证明促销欺诈事实 |
```

每次新增/修改证据，同步更新此表。

## 五、金额核算

### 核心原则：单一数据源
- 每个金额只在一处定义，其他位置引用
- 修改时必须全文搜索所有涉及金额的位置同步更新
- 标的额汇总行必须与各分项独立加总结果一致

### 验算检查清单
```
□ 诉讼请求总额 = 各案由金额之和
□ 各案由金额 = 该案由下各分项之和
□ 维权费用 = 公证+差旅+误工+保全+扫描等各分项之和
□ 差旅费 = 住宿+交通+铁路+误餐+补贴
□ 可期待利益 = 各项可期待利益之和
□ 证据清单中的金额与正文引用一致
□ 证据清单中的发票金额与正文引用一致
```

### 金额四舍五入规则
- 诉请金额可四舍五入到整数（如1,747.88→1,748）
- 但应在括号内注明精确金额和四舍五入
- 标的额总额保留到小数点后一位（法院立案系统要求）

## 六、法条核对

### 核对方法
1. **对照最新版原文**：不可凭记忆引用
2. **术语精确**：如新反法第39条是"举证责任转移"非"倒置"
3. **条文编号**：2025年修订的反法有大量新增条款，编号与旧版不同
4. **生效日期**：确认涉案行为发生时法律是否已生效

### 常用法律核对清单
- 反不正当竞争法（注意2025年修订版）
- 消费者权益保护法
- 民法典（合同编、侵权责任编）
- 民事诉讼法
- 最高法司法解释

### 法条引用格式规范
- 文中引用：`《反不正当竞争法》第十条第1款第1项`
- 括号内引用：`（《反不正当竞争法》第三十九条）`
- 多项法条：`（《反不正当竞争法》第十条、第十三条、第十四条）`
- **严禁**在法条编号后加"等"字模糊处理

## 七、策略决策框架

每个索赔/论证项必须明确归类（详见 [references/strategy.md](references/strategy.md)）：

| 类别 | 含义 | 写作位置 | 示例 |
|------|------|----------|------|
| **索赔项** | 写入诉讼请求，有金额 | 诉讼请求 | 可期待利益161,318.8元 |
| **论证项** | 写入事实与理由，无金额但支撑索赔 | 事实与理由 | 腾讯低于成本销售（新反法第14条） |
| **保留项** | 本案不主张，保留另行主张权利 | 事实与理由末段注明 | 分付年化16.6%保留另行主张 |
| **剔除项** | 不写入，记录决策理由备查 | 决策日志 | 商标费10,000剔除（系护城河非损失） |

**决策一经做出，记入决策日志（`memory/YYYY-MM-DD.md` 或工作区决策文件），不再重新讨论。**

## 八、多遍审定

### 五遍审定框架
| 遍数 | 审查重点 | 检查内容 |
|------|---------|---------|
| 1 | 逻辑一致性 | 前后论述是否矛盾、事实陈述与诉请是否对应 |
| 2 | 金额 | 各项金额加总、分项与汇总一致、证据清单与正文一致 |
| 3 | 法条 | 条文编号正确、术语精确、引用位置恰当 |
| 4 | 证据链 | 编号连续无跳号、引用格式统一、证据与论证对应 |
| 5 | 措辞 | 术语统一、错别字、标点、格式 |

### 审定前自动验证
运行验证脚本后再开始人工审定：
```bash
python3 scripts/validate.py <input.md>
```

验证项：
- 证据编号是否连续无跳号
- 金额汇总是否一致
- 法条编号格式是否规范
- markdown语法残留（如`**`未清除）

### 常见逻辑错误模式
- "原告二其余两个账号"→实际属于原告一（主体混淆）
- "未实际购买"→与合同订立表格矛盾（事实自相矛盾）
- 证据引用编号错误（如85写成86）
- 当事人代称不一致（"原告一"/"马晓明"/"原告"混用）

## 九、导出定稿

### Word导出
```bash
node scripts/md2docx.js <input.md> <output.docx>
```
依赖：`npm install docx`（已在skill目录下安装）

### PDF导出
```bash
python3 scripts/md2pdf.py <input.md> <output.pdf>
```
依赖：`pip3 install PyMuPDF`

### ⚠️ md2pdf.py 参数说明
脚本接受两个命令行参数：
- `sys.argv[1]`：输入md文件路径（必需）
- `sys.argv[2]`：输出pdf文件路径（可选，默认同名.pdf）

**注意**：脚本内`INPUT`/`OUTPUT`常量已被参数覆盖，无需手动修改脚本。

### 导出前检查
- 确认md源文件是最新版（检查修改时间）
- Word和PDF基于同一份md生成
- 导出后检查文件大小是否合理（docx通常50-100KB，pdf通常200-500KB）

### 版本管理规范
- **文件名版本号**：与文件内容版本保持一致，如内容已迭代至v19，文件名应为`诉状_v19_YYYYMMDD`
- **源md文件**：可使用固定文件名（如`诉状_v15_20260520.md`），但内容版本号在文末日期体现
- **导出后核对**：docx/pdf的文件属性→修改时间应与md一致
- **打包**：每次导出后重新打包zip，包含docx+pdf+md+证据清单

### 网上立案材料清单
- 诉状PDF签字扫描件
- 身份证明（身份证正反面）
- 证据清单
- 关键证据PDF（公证书、发票等）
- 委托手续（如有代理人）
